# KyHelper_Web — 双穹幻想 Burst 网页版日常助手

从模拟器版 `KyHelper`（ADB + scrcpy + 模板匹配）移植到 **云游戏网页版**
（Chrome + CDP + 模板匹配）。原来那 20 个任务、269 张模板、录制功能全部保留，
任务代码基本一行没改。

- 驱动对象：ERO LABS 云游戏页 `cloud_game.html?id=55`
- 识别方式：浏览器画面流 → 灰度模板匹配（和模拟器版同一套模板）
- 点击方式：CDP 合成鼠标事件，精确落在游戏画布上
- 界面形态：**本地网页控制台**（不用打包 exe，不用开投屏窗口）

---

## 一、跟模拟器版到底差在哪

| | 模拟器版 | 网页版（本项目） |
|---|---|---|
| 画面来源 | `adb exec-out screencap`（0.7s/次）+ scrcpy h264 | `Page.startScreencast`（48fps，无请求往返） |
| 点击 | `adb shell input tap` | `Input.dispatchMouseEvent`（浏览器内部，不抢鼠标） |
| 依赖 | MuMu + adb + scrcpy + PyAV + opencv | **Chrome + opencv + numpy + PyYAML** |
| 分辨率 | 死磕 2560×1440，换设备就重做模板 | 虚拟视口可任意设，坐标自动换算 |
| 返回键 | 安卓 keycode 4 | 见下面「网页版没有返回键」 |
| 界面 | 本地 web 控制台 + MJPEG 投屏 | 本地 web 控制台，**投屏默认关闭** |

省掉的整条链路：adb 进程、scrcpy-server.jar、h264 解码、PyAV、MJPEG 二次编码。
省掉的还有「每次决策截一张 350KB 的图」——现在识别直接吃浏览器合成器的帧。

## 二、快速开始

```bash
pip install -r requirements.txt
python run.py            # 或者双击 启动.cmd
```

会做这几件事：

1. 起本地控制台 `http://127.0.0.1:8765/`（端口被占自动往后找）；
2. 拉起一份**独立的 Chrome**（自己的 profile 在 `chrome-data/`，不动你平时的浏览器），
   直接打开云游戏页，窗口在左上角；
3. 把页面收拾干净：隐藏站点导航/页脚、游戏 iframe 铺满、
   虚拟视口设成 2560×1440，等价于模拟器截图；
4. 第一次需要在那个 Chrome 窗口里**登录一次**（登录状态会存在 `chrome-data/`，
   以后不用再登）。

> 为什么必须用独立 profile：Chrome 136 以后禁止在默认用户目录上开调试端口
> （`--remote-debugging-port`），所以只能给它一份自己的用户目录。
> 不想重新登录的话，把浏览器里 `erolabsjwt` 这个 cookie 的值填进
> `config.yaml` 的 `browser.jwt`，程序会自动种进去（见第四节）。

控制台里：左边勾任务、拖序号排序、设属性/难度；右边执行、看日志。
游戏本身就在旁边的 Chrome 窗口里，**默认不投屏**（省 CPU），
要预览点工具栏的「画面 关」→ 变成「画面 开」；录制任务时会自动打开。

命令行也留着：

```bash
python run.py --probe           # 环境自检：浏览器/画面/识别耗时/帧率
python run.py --shot            # 存一张当前画面到 logs/shots
python run.py -l                # 列任务
python run.py -t mail -t ruins  # 只跑指定任务
python run.py -t ruins --dry    # 只识别不点击
```

## 三、缩放自适应是怎么做的

这是移植里最容易埋坑的地方，单独说清楚。

**基准坐标系只有一个：模板的 2560×1440**。所有任务代码、所有模板 json、
所有手工坐标都活在这个坐标系里。下面是三道换算：

1. **视口 = 窗口本身**（不再覆盖成 2560×1440）
   以前用 `Emulation.setDeviceMetricsOverride` 把页面撑成 2560×1440，想让识别 1:1。
   代价是**虚拟视口比窗口大**：窗口只有 1427 CSS 宽，人只能看到左上角 1/1.8，
   用浏览器缩放看全之后内容又变成左上角对齐 —— 就是「显示不全 + 不居中」。
   现在视口老老实实等于窗口，位置交给下面这套「舞台」。

2. **精确量画布**（`core/browser.py`：`measure` / `_geo_from_frame`）
   这游戏是 Unity WebGL，DOM 套了三层：
   `页面 → iframe#game_frame → iframe#unityPlayer → canvas`，
   而且**画布被封顶在 ~1280×720**（比窗口小），默认还贴在容器上方。
   所以不能拿 iframe 的盒子当识别区域 —— 通过 OOPIF 调试会话
   （`Target.attachToTarget`）钻进游戏帧里量**画布真实矩形**，
   加上各层的偏移和缩放比，得到画布在父页面 CSS 坐标里的精确位置。

3. **加载后对齐一次**（`core/browser.py: settle_layout`）

   这游戏的画布被封顶在 1280×720，直接塞进大窗口就是一圈黑边 + 内容贴左上角。
   程序在加载完之后**只做一次**这套动作，之后不再碰画面：

   | 步骤 | 做什么 | 为什么 |
   |---|---|---|
   | ① 舞台 = 画布尺寸 | 舞台固定成量到的画布原生尺寸（1280×720） | 游戏按画布尺寸排版，内容就不会被裁 |
   | ② 撑满帧内层 | `#unityPlayer` 强成 `100vw × 100vh`（`_ensure_frame_css`） | 站点把它设成 inner+40×inner+80，画布右下角会被 iframe 裁掉 20/40 |
   | ③ 顶到原点 | 量「画布在哪、舞台在哪」，差多少平移多少 | 游戏自己给画布留了边距，不挪会被裁掉右下角 |
   | ④ 放大 | `browser.fill` 打开时把画面 `scale(k)` 到铺满窗口（k = min(窗口/画布)，**绝不超过窗口**） | 黑边基本没有 |
   | ⑤ 居中 + 锁定 | 按偏差平移居中；`_settled = True` | 之后不再动，只有窗口尺寸变化 / 重载游戏 / 点「重新对齐」才重做 |
   | ⑥ 验收 | 量一次「画布还在不在窗口里」，不在就退回上一版排布（没有就 1:1 铺满） | 宁可画面小一点，也**不许出现黑屏** |

   **什么时候做**：认到 **标题画面的 GAME 字样**（`assets/templates/title_logo.png`）
   就立刻动手 —— 这就是「加载完成」的那一刻，也是过场动画已经放完的时刻。
   认不到就退回两条老信号：主页锚点（`game.home_template`）出现，或画面静止
   两个周期（约 3 秒）。开始跑任务前如果还没对齐，会先补做一次。任何时候都可以
   点工具栏 **「重新对齐」** 手动再来一遍；**画面整块黑掉**就点 **「还原画面」**
   （只撤位移/缩放回到 1:1，不刷新页面、不用重新登录）。

   对齐只动 DOM/CSS，**不碰鼠标键盘、不抢前台、不改浏览器缩放**，运行期间
   你可以正常用电脑。

   > 关于「Ctrl + 滚轮 / 标题栏右键 → 缩放 → 放大」：这条路**不作为自动流程**。
   > 浏览器缩放是浏览器进程的快捷键，CDP 的合成事件（`Input.dispatchMouseEvent`
   > 带 modifiers=Ctrl）够不着它 —— 实测发 wheel 之后 `innerWidth` /
   > `devicePixelRatio` 一点没变；用 `Emulation.setDeviceMetricsOverride` 等效会
   > 把视口尺寸搅乱（舞台被撑到屏幕外、越缩越小）。
   > 真正能生效的只有系统级注入（`core/winput.py` 用 `SendInput` 发 `Ctrl+=` /
   > `Ctrl+0`），它会抢前台焦点，所以做成了**手动按钮「缩放 100%」**，
   > 不放进自动对齐流程（详见第 4 节配置那张表下面的说明）。

   几个坑（都写在代码注释里）：
   - **站点模板把 `#unityPlayer` 设成 `inner+40 × inner+80`**，比它所在的游戏帧还
     大；画布带着 `margin: 20px 0 0 20px` 摆在里面，结果画布右下角被 iframe 裁掉
     **右 20px、下 40px** —— 「首页底部那排按钮显示不全」就是这 40px。注意 iframe
     的内容是先按自己的盒子裁好再交给父页面摆的，在父页面挪 iframe 救不回来。
     解法是进帧里写一条 `#unityPlayer{width:100vw;height:100vh}`
     （`_ensure_frame_css`）：Unity 的容器本来就把画布那圈 20 的 margin 算进去了，
     `#unityPlayer` 一等于视口，画布就正好落在 `(0,0,1280,720)`，一个像素不裁。
     **千万别同时清画布的 margin** —— 清了画布会跑到 `(-20,-20)`，反而裁右下角。
   - 舞台样式只在 `prepare` 里注一次会被**页面导航冲掉**，所以用
     `Page.addScriptToEvaluateOnNewDocument` 注入；而注入的**只能是不带尺寸的
     基础样式** —— 带上尺寸的话，导航后会把注册那一刻的旧值（2560×1440）贴回去，
     舞台跑到屏幕外，表现就是「画面只显示一部分」；
   - 基础样式和舞台样式用**两个 `<style>`**（`__kyweb_css` / `__kyweb_stage`），
     否则会互相覆盖；
   - 改尺寸后 Unity 会**拆掉画布再重建**，那一两秒量不到画布，`_wait_canvas()`
     会等它回来，量不到就不居中（否则会把舞台推到 300px 外）；
   - k 必须用 `min(窗口/画布)` 且**不许超过窗口**：以前舞台已经是窗口大小了
     又乘 1.4，结果只看得见画面中间一块。
   - **对齐不能并发、位移不能不管**（2026-11-17 踩出来的黑屏）：跑完任务时
     `refresh_geometry(force=True)` 会重量窗口，如果那时候守护线程也在对齐，
     两边交替改 CSS，测量互相污染，位移被一路累加到 `(2052, 1155)` —— 游戏被
     整个推出窗口，用户看到的就是「游戏窗口全黑」。现在三道闸：`_settle_lock`
     保证同一时间只有一轮对齐；`_guard_shift` 把超过窗口 1/3 的位移直接削平
     （写 CSS 前必过）；⑥ 验收不过就回退。另外 `force=True` 只在**窗口尺寸真的
     变了**时才重排，尺寸没变只重量坐标（纯只读）。

4. **画面归一**（`core/capture.py: _fit`）
   截到的帧是「整个窗口」（2x 屏约 2560×1345），先按画布矩形裁掉黑边，
   再缩到 2560×1440。2x 屏上画布本身就是 1280×720 CSS × 2 = 2560×1440 像素，
   所以这一步基本是 1:1（切窗口大小时才真正缩放）。

5. **点击换算**（`core/device.py: tap` → `GameSession.to_css`）
   `css = 画布原点 + 基准坐标 × (画布实际尺寸 / 2560×1440)`

所以：

- 你把窗口拉大拉小、最大化、换显示器，任务一行都不用改（点完对齐一次即可）；
- 站点哪天改了布局 / 画布换了尺寸，`measure` 每次都会量到新的矩形，
  对齐逻辑跟着走；
- 任务里本来就有 `k = dev.screen().shape[1] / REF_W` 这种写法
  （主线/遗迹/召唤/异策战里都有），现在 `k` 恒等于 1，天然兼容。

**设备像素比**：保持系统原样（不强制 1x，否则 4K 屏上整个窗口小到看不清）。
画布按 dpr 原生分辨率出图，screencast 用 `maxWidth/maxHeight = 2560×1440` 封顶，
所以 2x 屏反而是「高分辨率降采样到模板尺寸」，比 1:1 更清晰。

窗口默认**最大化**（`browser.maximize`）。不想要就改成 `false`，那时按
`browser.window` 的尺寸开窗。

画布是游戏写死的 1280×720，窗口比它大时两个选择：

| 配置 | 效果 |
|---|---|
| `browser.fill: true`（默认） | 用 CSS 放大到铺满窗口 —— 黑边基本没有，但画面是插值放大的（略软） |
| `browser.fill: false` | 保持 1280×720 原生大小居中 —— 黑边大，但一个像素都不插值 |

没有「页面缩放」这个自动开关。需要的时候点工具栏 **「缩放 100%」**：

- 它做的是**系统级**操作 —— 真的发 `Ctrl+=` 再 `Ctrl+0`，所以浏览器一定会从
  90%（或任何比例）回到 100%，然后自动重新对齐一次画面。
- 为什么必须是系统级：`Ctrl+滚轮` / `Ctrl+=` / `Ctrl+0` 都是**浏览器进程**的
  快捷键，CDP 的合成事件只到渲染进程，实测发完 wheel 后 `innerWidth` /
  `devicePixelRatio` 一点没变。
- 代价：执行时会把游戏窗口抢到前台，**约 1~2 秒不能操作别的窗口**。所以默认
  只由用户点，不自动做。
- 想让它加载完自动做一次：`browser.zoom_auto: true`（每次页面加载只做一次）。
- 失败时日志会写明原因：找不到窗口 / 窗口没切到前台 / 系统拒绝模拟按键
  （安全软件或 UAC 拦了）/ 按键没生效。

> 顺带说明：**「画面显示不全」的真凶不是缩放**，是站点 Unity 模板把
> `#unityPlayer` 设得比游戏帧还大（见第 3 节）。缩放在旧版里是绕过这个 bug 的
> 土办法，现在根因修好了，缩放只是留作手动兜底。

## 四、登录（一次性）

四条路，任选：

1. **借用登录态**（最省事）：先在你平时那个 Chrome 里登录好游戏，然后在控制台点
   **「借用登录态」** —— 把那份 profile 的 cookie 拷进工具自己的 `chrome-data/`，
   重开浏览器就是已登录的。细节见下面「为什么不能直接用我平时那个浏览器」。
2. **手动登**（默认）：程序拉起 Chrome 后，在那个窗口里正常登录。
   cookie 存在 `chrome-data/` 里，之后每次启动都是登录态。
3. **粘 JWT**：F12 → Application → Cookies → `erolabsjwt`，复制值，
   填到 `config.yaml` 的 `browser.jwt`。程序启动时自动种 cookie 并刷新。
4. **重新登录**：哪天掉登录了，控制台日志会提示「请在弹出的浏览器窗口里登录一次」。

画面区会显示 `请在弹出的浏览器窗口里登录一次` —— 看到这行就是没登录成功。

### 为什么不能直接用我平时那个浏览器

不是没做，是**做不到**，两道硬门槛：

1. **CDP 只认带 `--remote-debugging-port` 启动的浏览器。** 外部程序（本工具、
   Playwright、DevTools 自动化都一样）要控制一个 Chrome，只能通过这个调试端口。
   你日常双击打开的那个 Chrome 没有端口，进程里也没有任何开关能事后加上 ——
   对别的程序来说它就是个黑盒。
2. **Chrome 136 起禁止在「默认用户目录」上开调试端口。** 官方这么改是为了防止
   恶意程序偷偷读 cookie。所以「关掉 Chrome，再用你的默认 profile 带端口启动」
   也会被忽略 —— 必须另给一个 `--user-data-dir`。这就是 `chrome-data/` 的由来。

两条加起来：**能控制的 profile 和你的日常 profile 天生不是一个。** 于是只能搬：

- **点「借用登录态」**（推荐）：把 `Local State`（DPAPI 加密的主密钥）+
  `Default/Network/Cookies`（密文）+ Preferences / Local Storage 拷进 `chrome-data/`。
  重开之后工具里就是已登录状态，`cf_clearance` 也一起带过来，连带跳过人机验证。
  旧的登录态会先备份到 `chrome-data/.import-backup/<时间戳>/`，随时能退回去。
  唯一的代价：**Chrome 开着时对 cookie 库是独占的**（实测连只读都 Permission denied），
  所以第一次点会问「要不要帮你关掉 Chrome」—— 关掉它的会话会保存，下次打开能恢复标签页。
- **粘 JWT**（上面第 3 条）：只搬 `erolabsjwt` 一个值，不用关浏览器，但 cookie
  过期了要再抄一次。
- **手动在那份 profile 里登一次**：不碰你日常浏览器，代价是可能过不了 Turnstile。

一句话：**登录态可以搬，窗口不能接管。**

### 登录页登不进去（錯誤代碼 1002 / 「請稍後重新再試」）

这里要先分清一件事：iframe 里显示的是**站点的会员登录页**
（`signup.html?type=webgl`），不是游戏服的登录。站点脚本拿到 `erolabsjwt`
这个 cookie 后才会去连云游戏；没登录时它就把这个账号页塞进 iframe。
所以「登不进去」= 站点会话没建立。

那个页面里有一张 Cloudflare Turnstile（「請驗證您是真人」）。在被自动化控制的
浏览器里它经常静默失败，表现为反复「登入失敗／請稍後重新再試」，甚至给个 `1002`。
这种情况**别反复试**（会触发频控），按下面顺序：

1. 先确认人机验证打了勾，再点登录；错一次就停，等一两分钟再试。
2. 点工具栏 **「重载游戏」**：清这份 profile 的 HTTP 缓存后重进账号页。
3. **最稳的一条**：点工具栏 **「借用登录态」**（把平时那个浏览器的 cookie 拷过来，
   连 `cf_clearance` 一起，最省事），或者点 **「登录令牌」** 粘 `erolabsjwt` 的值，
   直接建立会话，完全绕开登录页和人机验证。取法（用平时那个浏览器，别用工具的窗口）：
   打开并登录 `https://www.ero-labs.com` → F12 → Console → 输入 `document.cookie`
   → 复制 `erolabsjwt=...` 后面那段值。这个 cookie 不是 httpOnly，能直接读到。
4. 也可以在 `config.yaml` 的 `browser.jwt` 里填同一个值，启动时自动注入。

控制台状态里会带 `login_err`（如 `1002`），排错时先看这个码。

## 五、性能：具体省在哪，省了多少

都是在这台机器（2560×1440 视口）实测的数字。

| 环节 | 模拟器版 | 网页版 | 说明 |
|---|---|---|---|
| 取一帧画面 | `screencap` 350~700ms | **screencast 20~40ms** | 合成器直接推帧，无请求往返 |
| 画面帧率 | 识别 1.4fps / 投屏 60fps | **30fps（可配）** | 识别和投屏共用一个源；Chrome 不给你设帧率，只能 `everyNthFrame` 隔帧 |
| 单次识别（局部） | 3~5ms | **3.5~5ms** | 平手，但不用先截图 |
| 单次识别（全图兜底） | 50~200ms | **15ms** | 缩图粗搜 + 原图精修 |
| 画面解码 | 每帧 h264 解码 | **每 120ms 解一次 JPEG** | 按帧号+TTL 复用，一轮决策共用一帧 |
| 界面投屏 | 每帧重编 JPEG | **默认关闭** | 需要时才开，开也只做 1/2 分辨率解码 |

具体三招：

1. **ROI 优先**（`core/vision.py`）
   每张模板的 `.json` 里记着它当初是从画面哪个位置裁的（`x`/`y`）。
   先在那一小块 ±180px 里找，命中就走。
   实测局部匹配 3.5ms vs 全图 52ms，**快 15 倍**，而且误匹配更少。

2. **粗搜 + 精修**（`_coarse_find`）
   ROI 没命中才用：整幅图缩一半、模板也缩一半先扫一遍（像素少 4 倍、
   模板少 4 倍），锁定候选点后只把原图那一小块拿来重匹配。
   实测 15ms vs 52ms，位置和分数完全一致（1.000）。

3. **帧复用**（`core/capture.py`）
   screencast 一秒推 48 帧，但决策循环只有 3~4Hz。
   解出来的 BGR 图和灰度图都按帧号缓存，120ms 内反复取不重解；
   一轮决策里 N 次识别共用同一张灰度图。
   点完按钮后会**等新帧到手**再识别，避免拿着点击前的画面把同一步点两遍。

另外两个默认关闭的开关：

- `ui.preview: false` —— 不开投屏。游戏就在旁边窗口里，镜像一份纯属浪费；
- `template.roi: true` —— 关掉会退回全图搜索，只在排查「模板到底有没有」时才有意义。

### 画面流的帧率：唯一能砍掉好几个核的开关

Chrome 的合成器会按屏幕刷新全力推帧 —— 实测 **94fps × 2560×1440 JPEG**，
每帧 200~400KB，光编码 + base64 + 进程间传输就是 20~35 MB/s。而识别一次决策
本来就要 0.3~1 秒，而且永远只取「最新一帧」，90fps 纯属浪费（还会把显存压力
顶高，页面崩过一次）。

```yaml
capture:
  fps: 30        # 兼容旧配置；新机制用下面两个档位
  fps_high: 60   # 预览开/录制时的目标帧率（画面流畅）
  fps_low: 20    # 预览关时的目标帧率（省 CPU）
  quality: 55    # JPEG 质量，62→55 再省约 15% 体积
ui:
  fps_mode: auto # auto=跟随预览开关 / high=锁60 / low=锁省电20
```

**帧率跟随画面开关**（2026-11-21）：Chrome screencast 只有 `everyNthFrame`
整数隔帧（94/1=94、/2=47、/3=31），凑不出 60。所以：
- **high 档（60）**：源端全速推（nth=1）+ 接收端按时间戳限到精确 60 —— 录制/预览时
  画面跟手；`30fps 录制卡顿` 就是这个档解决的。
- **low 档（20）**：源端隔帧（nth≈5），编码/传输的 CPU 也省下来 —— 预览关时自动用。
- **auto（默认）**：预览开（含录制）自动切 60，关掉自动降 20，不用手动管。

顶栏帧率按钮点一下循环 `自动 → 60 → 省电`，选择会写回 `ui.fps_mode` 记住。
`/api/state` 的 `capture.fps_mode` / `target_fps` 能看到当前模式与目标帧率。
改 config 后不用重启：`POST /api/capture/apply` 重开画面流即可生效。

### 浮层模式（已关闭，仅作记录）

> **当前默认不启用**：`ui.overlay: false` / `ui.panel: true`，就是「游戏窗口 + 独立
> 助手窗口」两个窗口。浮层（把面板塞进游戏窗口右上角）实做出来了，但实际用下来
> 不好用 —— 会挡游戏右上角那排入口、能点的区域小、还得靠 `Ctrl+Shift+X/H`
> 记快捷键。代码留着没删，想再试把 `overlay` 改回 `true`、`panel` 改 `false`。

**为什么当初想合并**：机器人识别画面靠的是 `Page.startScreencast`，
而窗口一旦被最小化 / 完全遮住 / 挪到后台标签，Unity 就停止出帧（实测
`visibilityState: hidden` 时点击和渲染全停），机器人立刻变瞎。把游戏 iframe 嵌进
助手页面更糟：那是第二次 Unity 渲染，等于又开一个游戏实例，CPU/显存只会更高。
所以能合并的方向只有「把控制面板搬进游戏窗口」这一条。

```yaml
ui:
  overlay: true    # 本行是浮层模式的写法，默认已经改成 false
  panel: false     # 不再弹独立的 1280×860 助手窗口
```

浮层由 `Page.addScriptToEvaluateOnNewDocument` 直接执行（不受游戏站 CSP 限制），
UI 在 Shadow DOM 里（不受站点 CSS 影响），数据 fetch `http://127.0.0.1:8765`
（服务端已加 CORS + PNA 响应头）。源码在 `core/overlay.py` / `web/overlay.js`。

两条设计约束：

1. 机器人按**绝对坐标**点击，浮层只要接收点击就会把那一下吃掉。所以**跑任务时**
   浮层缩成右上角一条小字，整块 `pointer-events: none` —— 绝不抢点击；
   要停止按 **Ctrl+Shift+X**，要看日志按 **Ctrl+Shift+H** 展开（展开后仍不接收点击）。
2. 浮层是锦上添花：装不上（页面没加载完、站点改结构）就自动回落到独立面板窗口
   （启动后 ~30 秒兜底检查），不会让你对着一个没有界面的程序发呆。
   想固定用独立窗口就把 `overlay` 改 `false`、`panel` 改 `true`。

**「浮层闪一下就没了」是怎么回事**：云游戏壳在启动过程中会换一次 DOM
（实测是 `document.open()/write()`），挂在 `<html>` 下的浮层节点会被一起清掉。
以前只看 `window.__kyov_ok` 这个记忆位，被清掉一次就再也不回来了。现在三层兜底：

| 层 | 谁 | 什么时候 |
|---|---|---|
| 页面内守活 | `web/overlay.js` 里 `setInterval(…,800)` | 节点从文档里掉了就原地挂回去（Shadow DOM 和勾选都还在，不会重建） |
| 服务端巡检 | `GameSession.ensure_overlay_alive()` | 空闲时每 3 秒探一次 `#kyov`，不在了补注一张 |
| 兜底窗口 | `_open_panel_if_overlay_failed()` | 连补 6 轮（约 30 秒）仍装不上，才开独立面板；优先在**游戏那个 Chrome 实例**里开窗，不额外起进程 |

补注是"先探活、后重建"：浮层还活着就什么都不做（重建会清掉用户勾的任务和
已经滚出来的日志）；真被清掉了才重建，且旧实例的守活器会自己退场，不会堆出两份。

### 运行期间去做别的事

窗口**不会被挪走了**（那个「挪到屏幕外」的行为已经删掉 —— 窗口凭空消失体验太差）。
现在就是老老实实摆在那儿，你该干什么干什么，挡着就挡着（它不需要聚焦、不需要置顶）。

实测三种窗口状态下的出帧情况（同一台机器、同一段动画画面）：

| 窗口状态 | screencast 出帧 | 结论 |
|---|---|---|
| 正常可见 | 71~95 fps | 正常 |
| **被其他窗口盖住** | 71~95 fps | 正常（已经关掉遮挡降频） |
| **最小化 / Win+D** | **0~0.6 fps** | 断了，任务会卡住 |

唯一要防的是最小化：跑任务时守护线程每 1.5 秒看一眼，发现窗口被最小化就
**原地恢复**（不挪位置、不改大小），帧率立刻回到 70+fps。所以按了 Win+D
也不至于把任务弄死，只是那 1~2 秒画面是停的，正好卡在某个「等待出现」上
可能会超时一次。

一个坑：**别把窗口缩得太小**（320×200 时 Chrome 会把画面流降级，帧掉到 614×330，
识别就不准了）。

## 六、网页版没有返回键（重要）

模拟器版里 `dev.back()` 是安卓 keycode 4。**浏览器里没有这个东西**，
所以 `core/device.py: back()` 按顺序试三招：

1. 界面上有返回箭头模板（`btn_back` / `btn_back_relic` / `btn_story_back`）→ 点它；
2. 发 `Escape`（部分 WebGL 游戏认）；
3. 点 `game.back_point`（默认左上角 `(70,70)`，就是大多数页面的返回箭头位置）。

实战建议：**能点底部「首页」标签就别用返回键**。
`core/flows.ensure_home()` 本来就是优先点 `tab_home` 的，返回键只是兜底。
如果某个任务的返回键点了没反应，用录制功能把那个页面的返回箭头录成模板，
命名 `btn_back` 放进 `assets/templates/`，`back()` 会自动优先用它。

## 九、排错

| 现象 | 原因 / 处理 |
|---|---|
| 画面区显示「请在浏览器窗口里登录一次」 | 没登录。在工具拉起的 Chrome 里登录，或填 `browser.jwt` |
| 登录页弹「登入錯誤 · 錯誤代碼 1002」或「請稍後重新再試」 | 工具这份 profile 里人机验证过不去（平时用的浏览器能登是正常的）。别反复试，直接点「登录令牌」粘 `erolabsjwt` |
| 画面区显示 `请在弹出的浏览器窗口里登录一次` 但窗口里明明是游戏画面 | 状态还没刷新（最多 1.5s），或游戏框里还留着登录遮罩 |
| `--probe` 说「浏览器起来了但调试端口没响应」 | 9222 被别的程序占了，改 `browser.port` |
| 帧率掉到个位数 / 画面冻住 | Chrome 窗口被最小化了。最小化时浏览器停止合成，**别最小化**（遮挡没事，已关掉遮挡暂停） |
| 点击点了没反应 | 先 `--probe` 看「游戏区域」是不是 `0,0 2560×1440`；不是的话说明站点改了布局，把日志发我 |
| 识别老是「超时」但画面上明明有 | 模板是模拟器 2560×1440 裁的，网页版渲染细节略有差异。用录制功能重录那一步，或把 `template.threshold` 降到 0.80。**重录完不用重启进程**：模板缓存会按文件时间自动重载（`core/vision.py` 的 `_load/_forget`），保存即可再跑 |
| 明明有可参加的战，日志却说「清单里没有可参加的战」 | **先看游戏语言**。站点有简/繁开关，模板基本都是简体录的；切到繁体后「參加」的笔画整片错位，相似度从 0.99 掉到 **0.57**（同一帧里纯图标模板仍有 0.91，所以只有带字的按钮会挂）。改回简体即可；`btn_join_bp.png` 是备用的繁体版，两个都留着是为了两种语言都能用 |
| 特典页明明有「派遣」卡片，却报「没找到 [派遣] 卡片」 | 同上，**语言问题**。`派遣`/`全部领取` 这些纯文字模板在另一种语言下只有 0.73~0.84，卡在 0.85 门槛下。现在每张都备了 `_trad` 繁体版：`card_dispatch(_trad)`、`title_dispatch(_trad)`、`btn_dispatch_claim_all(_trad)`，`tap_any/exists_any` 会自己挑认得出的那套。日志里会打印最高分，看到「最高 xx 0.7x」就是语言变了 |
| 圣骑士明明有感叹号，却「羁绊页签没有感叹号，本轮不送」 | 旧版用 `if: gift_badge` 判断，可详情页 **被动能力/技能/装备/羁绊四个页签都是同一个粉色感叹号**，模板只有 36×36，得分 0.86~0.90 正好压在 0.88 门槛上。现在改成 `tasks/paladin.py`：不看感叹号，直接看羁绊页有没有**糖果**；遇到只有「突破（要花束）」的角色就点面板右边的 `›` 换下一个，最多试 6 个，都不行就跳过并在日志/通知里提示 |
| 录制任务（如疾走讨伐战/异界战SR）「等待 rec_task_XX_08/10 超时 6s」失败，失败截图是战斗画面（WAVE 或 TIME） | 录制时你是**手动等战斗打完**才点下一步「关闭」，但那段等待没被录进步骤。回放时脚本点完「出击」立刻找「关闭」，6 秒就超时，而战斗其实刚开始（时长几秒到三五分钟不等）。现在录制解释器在「某步找不到按钮」时会先看是不是进了战斗，是就**自动等它打完再重试这一步**，且不会去重点上一步的「出击」（避免重复消费次数）。**两种战斗 HUD 都认**：`battle_hud`（橙色 WAVE，疾走讨伐战）、`battle_time_flag`（橙色 TIME，异界战SR）——只认一个会漏（异界战SR 曾因此没等到战斗、6s 超时后连按返回卡死）。等待上限 10 分钟、期间只等不点、全程响应「停止」，绝不因「等太久」提前放弃。另外 `ensure_home` 新增结算页兜底：卡在 Result 页时按[关闭]位置关掉，不再只按返回键（返回键关不掉结算页）。通用修法，不用重录；普通步骤零额外开销 | 云游戏网页版的弹窗/页面切换有自己的动画，动画那零点几秒里点的下一下会被游戏吞掉。现在：全局点击间隔调大（`config.yaml` 的 `input.delay_min/max`，0.35~0.85 → 0.55~1.10），录制脚本每步点完再多等 0.45s；某步「等不到东西」时，若上一步点的按钮还在画面上（说明那一下没生效），自动重点一次再等，最多两轮；按钮已经不在就不乱点，避免重复消费。救援战筛选的勾选也改成「点完回读状态，没勾上补点」 |
| 救援战连打几场后卡在「报酬一览」页、接着「不在救援清单了」「回不到主页」连锁失败 | 打完某场时点[关闭]的相似度只有 0.878（其它场 0.998）——点在了动画中间/按钮边缘，游戏没吃掉。旧代码 `tap_img` 返回 True 就当关掉了，结果停在「报酬一览」**模态面板**上，返回键关不掉、还盖住主页锚点，一路按返回到超时。现在：`collect_reward` 点完[关闭]必须**回读 `title_reward` 确认真消失**，没消失就按最新找到的位置再点（0.90 找不到降到 0.80），最多 3 次；`ensure_home` 也加了兜底——认出报酬页会按[关闭]位置关掉。实测 `title_reward` 只在报酬页 0.997、其它页 ≤0.43，不会误关 |
| 免费召唤抽完停在「召唤结果」页不关，接着每个任务都报「回不到主页」 | 「召唤结果」横幅一开场就出来了，但面板和右下角[关闭]要等抽卡动画放完才滑进来。旧代码一看到横幅就去找[关闭]，找不到就判「没等到结果页」，弹窗留在屏幕上，后面所有任务全撞死。现在：横幅只当「进到流程了」，接着点右上角 SKIP 跳动画、轮询等[关闭]、点完还要确认面板真消失；`ensure_home` 里也加了兜底，任何任务半路遇到这个弹窗会先关掉它 |

## 十、风险

自动化违反绝大多数游戏用户协议，有封号风险。
保留随机延迟（默认 0.35~0.85s）、别 24 小时挂着、别用于账号交易。
